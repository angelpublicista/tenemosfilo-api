═══════════════════════════════════════════════════════════════════════════════
TENEMOS FILO — VARIABLES DE ENTORNO
═══════════════════════════════════════════════════════════════════════════════

Referencia de las dos aplicaciones del proyecto:

  API    tenemosfilo-api      Express + Prisma + Postgres    archivo .env
  FRONT  tenemos-filo-front   Next.js 16 + NextAuth v5       archivo .env.local

Aquí no hay ningún valor real: todo son marcadores. Los valores verdaderos
viven solo en el .env de cada máquina y en el panel del proveedor de deploy.

Cada variable está marcada así:

  [OBLIGATORIA]  sin ella la aplicación no arranca
  [RECOMENDADA]  arranca, pero algo deja de funcionar (se explica qué)
  [OPCIONAL]     tiene un valor por defecto razonable
  [HEREDADA]     de una etapa anterior del proyecto; ver la sección 3


═══════════════════════════════════════════════════════════════════════════════
1. API — tenemosfilo-api/.env
═══════════════════════════════════════════════════════════════════════════════

El API valida su configuración al arrancar (src/config/env.ts). Si falta algo
obligatorio no levanta a medias: escribe qué falta y se detiene.

─── 1.1 Básicas ──────────────────────────────────────────────────────────────

NODE_ENV=development                      [OPCIONAL]  development | test | production
PORT=4000                                 [OPCIONAL]
LOG_LEVEL=info                            [OPCIONAL]  fatal|error|warn|info|debug|trace

CORS_ORIGIN=http://localhost:3000         [RECOMENDADA]
    Orígenes del front que pueden llamar al API, separados por coma. Si no
    coincide con el dominio real, el navegador bloquea todas las peticiones.

APP_URL=http://localhost:3000             [RECOMENDADA]
    URL pública del front. Con esto se arman los enlaces que van DENTRO de los
    correos (botón "Ver mi reserva", enlace de recuperar contraseña). Si queda
    en localhost, los correos de producción llevarán enlaces rotos.

─── 1.2 Base de datos ────────────────────────────────────────────────────────

Hay tres formas de decir a qué base conectarse. El orden de precedencia importa
y es el mismo que usa la CLI de Prisma (scripts/resolve-db-url.mjs):

    1º  DATABASE_URL          si está definida, manda sobre todo
    2º  DB_TARGET=local       usa DATABASE_URL_LOCAL       ← por defecto
    3º  DB_TARGET=production  usa DATABASE_URL_PRODUCTION

DATABASE_URL=                             [OBLIGATORIA, si no hay DB_TARGET]
    postgresql://usuario:clave@host:5432/basededatos
    Es lo que inyectan los servicios de deploy.

DATABASE_URL_LOCAL=postgresql://…         Base de desarrollo
DATABASE_URL_PRODUCTION=postgresql://…    Base de producción
DB_TARGET=local                           local | production

    El valor por defecto es 'local' a propósito: arrancar sin configurar nada
    debe pegarle a la base de desarrollo, nunca a la de producción.

─── 1.3 Autenticación ────────────────────────────────────────────────────────

NEXTAUTH_SECRET=                          [OBLIGATORIA]  mínimo 16 caracteres
    Firma los JWT de sesión (HS256). TIENE QUE SER EL MISMO VALOR que el
    NEXTAUTH_SECRET del front, o el API rechazará todas las sesiones.
    Generar con:  openssl rand -base64 32

GOOGLE_CLIENT_ID=                         [RECOMENDADA]
GOOGLE_CLIENT_SECRET=                     [RECOMENDADA]
    Solo si se quiere "Entrar con Google". Sin esto el resto del login
    funciona normal. Las mismas credenciales van en el front.

─── 1.4 Correo transaccional — ZeptoMail (Zoho) ──────────────────────────────

Mueve la recuperación de contraseña y todos los avisos de reserva: reserva
nueva, confirmación, cancelación, reprogramación y pago.

ZEPTOMAIL_TOKEN=                          [RECOMENDADA]
    OJO: es el "Send Mail Token" del agente, NO la API key de la cuenta Zoho.
    Sale de:  ZeptoMail › Mail Agents › [tu agente] › Setup › Send Mail Token
    Se puede pegar con o sin el prefijo "Zoho-enczapikey", da igual: el código
    lo normaliza. (Pegarlo dos veces daba un 401 que no explicaba nada.)

ZEPTOMAIL_FROM_EMAIL=noreply@tenemosfilo.com    [RECOMENDADA]
    Tiene que ser un remitente verificado dentro del dominio del agente.

ZEPTOMAIL_FROM_NAME=Tenemos Filo          [OPCIONAL]

ZEPTOMAIL_API_URL=https://api.zeptomail.com/v1.1/email    [OPCIONAL]
    Solo si la cuenta está en un centro de datos regional en vez del global:
    https://api.zeptomail.eu/v1.1/email    (Europa)
    https://api.zeptomail.in/v1.1/email    (India)

    SI FALTAN ESTAS VARIABLES NO SE CAE NADA. Los envíos quedan registrados en
    el log y la operación sigue: una reserva nunca se pierde por no poder
    avisar. Pero el comensal no recibe ni confirmación ni comprobante.

    Y ojo: tener el token no basta para que llegue correo. Hay que verificar el
    dominio en ZeptoMail y publicar los registros SPF y DKIM en el DNS. Sin
    eso el token autentica pero los envíos se rechazan o caen en spam.

─── 1.5 Almacenamiento de archivos — AWS S3 ──────────────────────────────────

AWS_REGION=us-east-1                      [OPCIONAL]
AWS_ACCESS_KEY_ID=                        [RECOMENDADA]
AWS_SECRET_ACCESS_KEY=                    [RECOMENDADA]
S3_BUCKET=                                [RECOMENDADA]
    Sin esto no se pueden subir logos, portadas ni fotos de experiencias.

S3_PUBLIC_URL_BASE=                       [OPCIONAL]
    Dominio público del CDN (CloudFront u otro). Si se deja vacío se usa el
    endpoint estándar https://{bucket}.s3.{region}.amazonaws.com

UPLOADS_MAX_BYTES=10485760                [OPCIONAL]  10 MB
    Límite duro del servidor. El front también valida, pero esta es la que
    manda: la del front se puede saltar.

─── 1.6 Red y proxy ──────────────────────────────────────────────────────────

TRUST_PROXY=0                             [IMPORTANTE EN PRODUCCIÓN]
    Cuántos proxies hay delante del API. En local 0; detrás de Nginx o de un
    balanceador normalmente 1.

    Si se deja en 0 con un proxy delante, el API ve la IP del proxy en vez de
    la del visitante: el límite de peticiones por IP contaría a TODOS los
    visitantes como si fueran una sola persona, y bastaría un poco de tráfico
    para bloquear el sitio entero.

2. FRONT — tenemos-filo-front/.env.local
═══════════════════════════════════════════════════════════════════════════════

─── 2.1 Conexión con el API ──────────────────────────────────────────────────

API_URL=http://localhost:4000             [OBLIGATORIA]
    La usa el servidor de Next (proxy y rutas de auth). No se expone al
    navegador, así que puede ser una dirección interna de la red privada.

NEXT_PUBLIC_API_URL=http://localhost:4000 [OBLIGATORIA]
    La misma dirección, pero para el navegador. Tiene que ser accesible desde
    fuera. Todo lo que lleve el prefijo NEXT_PUBLIC_ viaja al cliente y es
    público: nunca poner un secreto ahí.

NEXT_PUBLIC_APP_URL=http://localhost:3000 [RECOMENDADA]

─── 2.2 Autenticación ────────────────────────────────────────────────────────

NEXTAUTH_SECRET=                          [OBLIGATORIA]
    EL MISMO VALOR que en el API. Si los dos no coinciden, el login parece
    funcionar pero cada llamada al API responde 401.

NEXTAUTH_URL=http://localhost:3000        [OBLIGATORIA EN PRODUCCIÓN]
    URL canónica del front. Necesaria si el deploy está detrás de un proxy.

GOOGLE_CLIENT_ID=                         [RECOMENDADA]
GOOGLE_CLIENT_SECRET=                     [RECOMENDADA]
    Las mismas credenciales que el API. En la consola de Google hay que
    registrar la URI de retorno:
        http://localhost:3000/api/auth/callback/google
        https://TU-DOMINIO/api/auth/callback/google

─── 2.3 Correo transaccional — ZeptoMail ─────────────────────────────────────

ZEPTOMAIL_TOKEN=                          [RECOMENDADA]
ZEPTOMAIL_FROM_EMAIL=                     [RECOMENDADA]
ZEPTOMAIL_FROM_NAME=Tenemos Filo          [OPCIONAL]
ZEPTOMAIL_API_URL=…                       [OPCIONAL]

    Son LAS MISMAS variables que el API (sección 1.4), a propósito: si las dos
    aplicaciones se despliegan juntas, el correo se configura una sola vez.

    El grueso del correo lo manda el API. Aquí solo queda lo que se compone en
    el front y no tiene endpoint propio: las cotizaciones del CRM. Si algún día
    las cotizaciones se guardan, ese envío debería mudarse al API y estas
    variables desaparecerían del front.

─── 2.4 Servicios externos ───────────────────────────────────────────────────

NEXT_PUBLIC_RECAPTCHA_SITE_KEY=           [RECOMENDADA]
    Protege los formularios de registro y login. Se saca en
    https://www.google.com/recaptcha/admin

OPENAI_API_KEY=                           [OPCIONAL]
OPENAI_MODEL=                             [OPCIONAL]
    Solo para el generador de descripciones de experiencias con IA
    (/api/ai/generate-description). Sin la clave, esa función no está
    disponible; el resto del panel funciona igual.
    No está configurada en local ahora mismo.

ZOHO_CLIENT_ID=                           [OPCIONAL]
ZOHO_CLIENT_SECRET=                       [OPCIONAL]
MICROSOFT_CLIENT_ID=                      [OPCIONAL]
MICROSOFT_CLIENT_SECRET=                  [OPCIONAL]
    Integraciones de calendario (Zoho y Outlook). Las rutas OAuth existen pero
    la integración no está terminada ni configurada.

3. HEREDADO — variables de etapas anteriores
═══════════════════════════════════════════════════════════════════════════════

Estas siguen en el .env.local y en el env.example del front, pero conviene
saber en qué estado están antes de copiarlas a un servidor nuevo.

─── Firebase ─────────────────────────────────────────────────────────────────

NEXT_PUBLIC_FIREBASE_API_KEY, _AUTH_DOMAIN, _PROJECT_ID, _STORAGE_BUCKET,
_MESSAGING_SENDER_ID, _APP_ID, FIREBASE_ADMIN_CLIENT_EMAIL,
FIREBASE_ADMIN_PRIVATE_KEY

    La autenticación pasó a NextAuth y las notificaciones pasaron al API. De
    todo Firebase solo queda vivo el flujo de verificación de correo
    (/verify-email); es lo único que justifica mantener estas variables.

    Ya no lo llama nadie:
        · /api/notifications                     leía Firestore (usa FIREBASE_ADMIN_*)
        · src/lib/firebase/notificationService.ts  sin ningún import

─── Brevo — ELIMINADO DEL PROYECTO ───────────────────────────────────────────

BREVO_API_KEY, BREVO_FROM_EMAIL, BREVO_SMTP_USER, BREVO_SMTP_PASSWORD,
BREVO_TEMPLATE_WELCOME_ID, BREVO_TEMPLATE_PASSWORD_RESET_ID,
BREVO_TEMPLATE_EMAIL_VERIFICATION_ID

    Ya no queda ni una línea de código que use Brevo, ni en el API ni en el
    front. Todo el correo sale por ZeptoMail.

    Si estas variables siguen en el .env.local o en el panel del deploy, se
    pueden borrar: no las lee nadie.

─── Sanity — ELIMINADO DEL PROYECTO ──────────────────────────────────────────

NEXT_PUBLIC_SANITY_PROJECT_ID, NEXT_PUBLIC_SANITY_DATASET,
NEXT_PUBLIC_SANITY_API_VERSION, NEXT_PUBLIC_SANITY_TOKEN

    Ya no queda código que use Sanity. Se puede borrar todo del .env.local.

    ATENCIÓN con NEXT_PUBLIC_SANITY_TOKEN: empieza por "ske", que en Sanity
    significa permiso de ESCRITURA, y el prefijo NEXT_PUBLIC_ hace que ese
    tipo de variable se incruste en el JavaScript que descarga el navegador.
    No llegó a filtrarse porque ningún archivo lo usaba —Next solo incrusta
    las que aparecen en el código, y se verificó buscándolo en el bundle—,
    pero conviene revocarlo en Sanity en vez de solo borrarlo del archivo.

─── Variables documentadas que ya no lee nadie ───────────────────────────────

    RECAPTCHA_SECRET_KEY                   está en .env.local y en env.example
    NEXT_PUBLIC_BREVO_TEMPLATE_WELCOME_ID  está en env.example

    Ningún archivo de src/ las lee. Se pueden borrar sin efecto.

    Nota sobre reCAPTCHA: la clave pública (SITE_KEY) sí se usa, así que el
    widget aparece, pero al no haber nada que valide la respuesta contra
    Google en el servidor, hoy no está filtrando nada.

4. PENDIENTE PARA PRODUCCIÓN
═══════════════════════════════════════════════════════════════════════════════

Configuración que todavía no está puesta en el servidor:

    API    TRUST_PROXY=1              o el sitio se bloquea solo con tráfico
    API    ZEPTOMAIL_TOKEN            + verificar dominio con SPF y DKIM
    API    ZEPTOMAIL_FROM_EMAIL       remitente verificado
    API    APP_URL                    o los correos llevan enlaces a localhost
    FRONT  ZEPTOMAIL_TOKEN            mismas credenciales que el API
    FRONT  ZEPTOMAIL_FROM_EMAIL       o el CRM no puede mandar cotizaciones
    FRONT  GOOGLE_CLIENT_ID / SECRET
    AMBOS  quitar todas las BREVO_*   ya no las lee nadie
    AMBOS  llaves reales de Wompi y su webhook configurado

Y fuera de las variables de entorno, quedan diez migraciones sin aplicar en la
base de producción:

    audit_log, commissions, payouts, wompi_settings, embed_domains,
    company_operation_settings, channel_listings, company_previous_slugs,
    company_cover, add_notifications

    Se aplican con:  DB_TARGET=production npm run prisma:deploy
